--------------------------------------------------------------------------------
1. 왜 이 프로브가 필요했나 (dev 결론이 정정된 경위)
--------------------------------------------------------------------------------

TASK-005의 1차 하네스(`AnalysisStatisticsConcurrencyTest`의 P1 최종값 케이스)는
**스레드당 2,000~20,000회 루프**를 돌리는 형태였고, 스레드 16/64/256 x 반복
2,000/20,000 x yield/스핀 조합까지 넓힌 125라운드에서 P1 최종값 손실이 **0건**이었다.

그러나 실제 `MainApiController.runAnalysis()`는 루프가 아니다 —
**파일 1개 = 태스크 1개 = 증가 -> 대입 1회**다. 루프 하네스에서는 종반의 대입이 전부
최댓값 근처라 최종값이 자연히 수렴하므로, **결함이 있어도 0이 나온다.**
즉 "결함이 없어서 0"이 아니라 "결함이 드러나는 지점을 비켜가서 0"이었다.

실경로를 모델링하자 손실이 재현됐다. 그 실행 결과가 아래 3절이다.
(work-order v2 §0.5.1 / §0.8, `05-dev-progress.md` 1038~1123행)

--------------------------------------------------------------------------------
2. 모델 정의 (프로브가 무엇을 흉내냈는가)
--------------------------------------------------------------------------------

  - 파일 N개 = 태스크 N개. N ∈ {2, 3, 5, 8} (1차 프로브는 {2,3,5,8,16,30})
  - 각 태스크는 **증가 -> 대입 1회**만 한다 (루프 없음)
        int v = ext.incrementAndGet();   // 외부 AtomicInteger — 실소스의 successCount
        [gap]                            // 증가와 대입 사이의 실제 작업
        set(v);                          // plain int 필드에 대입 — 실소스의 setSuccessCount(sc)
  - [gap] = `Thread.onSpinWait()` 1회. 실소스에서 증가와 대입 사이에 존재하는
    `session.getStatistics()` 호출 등 **실제 작업**을 흉내낸 것이다.
    "[간격없음]" 케이스는 이 한 줄이 없는 것이다.
  - N개 태스크는 `CountDownLatch`로 **동시에 출발**시키고, 전부 끝난 뒤 최종값을 읽는다.
  - 최종값 != N 이면 "손실 1회"로 센다. 손실량 = N - 최종값.
  - 한 설정당 시행 100,000회(1차 프로브는 20,000회).

  대응하는 실소스(작업 시작 커밋 6d9673e 기준):
    runAnalysis()       1482-1483행  int sc = successCount.incrementAndGet();
                                     session.getStatistics().setSuccessCount(sc);
    runAnalysis()       1487-1488행  setSkipCount 동일 패턴
    runAnalysisResume() 1759 / 1763행 같은 패턴의 2번째 사본

4. 재실행 방법 (시행 수만 올리면 된다)
--------------------------------------------------------------------------------

  1) 아무 임시 디렉터리에 복사하고 확장자를 되돌린다
       cp src/test/resources/concurrency/P1Probe2.java.txt /tmp/P1Probe2.java
  2) `main()`의 `100000`을 원하는 시행 수로 바꾼다 (이 값 하나만 바꾸면 된다)
  3) 단일 파일 소스 실행 (JDK 11+)
       java /tmp/P1Probe2.java

  손실률이 0.002~0.012% 수준이므로 **시행 수가 10,000 미만이면 0이 나오는 것이 정상**이다.
  0이 나왔다고 "재현되지 않는다"로 결론내지 말 것 — work-order v2 §0.8.

  같은 모델을 JUnit 하네스 안에 옮겨 둔 것이
  `AnalysisStatisticsConcurrencyTest#수정전_패턴P1_실경로모델_파일당_증가대입_1회에서_최종값_손실을_관측한다`
  이며, 시행 수는 그 클래스의 `REALPATH_TRIALS_PER_FILE_COUNT` 상수 하나로 조절한다.

--------------------------------------------------------------------------------
5. 이 근거의 한계 (과대해석 금지 — work-order v2 §0.5.1 (4))
--------------------------------------------------------------------------------

  - 이 프로브는 실클래스 `AnalysisStatistics`가 아니라 **동일 패턴을 흉내낸 static
    int 필드**를 썼다. 매커니즘("plain int 필드에 대한 증가 -> 대입 경합")은 같지만
    실클래스로 재현한 것은 아니다.
    (JUnit 하네스 쪽 실경로 모델 케이스는 이 한계를 없애기 위해 **실클래스**를 쓴다.)
  - 실사용 관측치(51회 중 5회 ≈ 10%)와 이 프로브의 손실률(0.002~0.012%)은
    **3~4자릿수 차이**가 난다. 실환경은 실제 I/O·GC·JIT 때문에 경합 창이 훨씬 넓기
    때문으로 보이나, **이 차이 자체는 규명하지 않았다.**
    이 프로브가 보인 것은 "매커니즘이 실재한다"까지이고,
    "실사용 발생률이 얼마인가"는 보이지 못했다.
  - 따라서 이 지표를 **회귀 게이트(단언)로 승격하지 않는다**(work-order v2 §11).
    회귀 게이트는 TASK-006의 폴링 stale read(결정적 0) + 최종값 32,000 단언이 담당한다.
